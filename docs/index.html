One frame per state: adapting the TLA+ Animation module to RxJS

A trace is a sequence of states. A view is a pure function from a state to a picture. An animation is one frame per state. That is the entire idea behind Will Schultz's Animation module for TLA+, and it transfers to RxJS one to one, because the operator specs and runtime tracers in this account already treat an Observable as a state machine.

Verdict
  • It adapts directly. The module's one real idea, state → view → frame, needs no translation; only the renderer and the playback move from TLA+ strings and jQuery to TypeScript.
  • The model side is nearly free. tla-ts counterexamples from rxjs-operator-tla already carry a full state and an action name per step, which the original module had to bolt on by hand.
  • The runtime side needs one new piece. An execution log is a list of actions, not states, so it must be folded into per-step snapshots first. That fold is scan.
  • First step: an SVG frame renderer and a stepper page on top of trace-to-marble.mjs, animating the four bug demos in the specs manifest.

What the Animation module does

The module is 170 lines of TLA+. It defines SVG primitives as records of the shape [name, attrs, children]: Line, Circle, Rect, Text and Group. A user writes a View, an ordinary state expression over the spec's variables that returns one such element tree. Two wrappers, AnimatedInit and AnimatedNext, add three auxiliary variables to the spec: a running SVG string, a frame counter and an optional action name. On every step the wrapper evaluates View in the new state, serialises the tree to a string and appends it. The last state of any TLC error trace therefore contains every frame.

Playback is a static HTML template. Each frame is a top-level <g> inside one <svg>; the page shows one group at a time and hides the rest, driven by Prev and Next buttons and the arrow keys. Every frame also carries a Next Action text label so the viewer knows which transition produced it.

Three facts in the code matter for the adaptation.

  • The frame contract is trivial. Any sequence of top-level groups inside one SVG is an animation. The newer template does not even read ids; it takes the first-level children in order.
  • Action names are a hack in the original. The spec author must write Next /\ ActionName("MoveElevator") per disjunct. TLC's trace explorer and tla-ts both report the action per step for free.
  • The author retired the string-building design. The README calls the auxiliary-variable version obsolete twice: first for TLC's command-line trace exploration with the CommunityModules SVG.tla, then for tla-web, where a JavaScript TLA+ interpreter renders the View live in the browser with interactive next-action choice.

What the talk adds

The 2018 TLA+ Community Event talk frames the purpose precisely. Specs serve three ends: communication, learning and verification. Animation targets the first two and leaves verification alone. The two demos are the ones in this repository's examples folder, and each stands for a use case.

The mapping onto existing work

The TLA+ pipeline has three stages: produce a trace, obtain a state per step, render each state. The repositories in this account cover all three on two tracks, one from the formal model and one from the running program.

Proposed architecture

One frame-state type, two adapters that produce it, one renderer, one animator. The model track fills frames straight from tla-ts; the runtime track folds events into frames. Everything to the right of the frame array is shared, which is what makes a side-by-side view of model and runtime possible later.

The frame-state type

The shape copies the specs' own vocabulary so that a frame from either track looks the same to the renderer. Stream variables mirror RxBase.tla: an append-only value sequence plus a status.

interface StreamState {
  vals: readonly unknown[];                       // delivered so far, append-only
  status: 'active' | 'complete' | 'error';        // RxBase.tla Status
}

interface FrameState {
  step: number;                                   // index in the trace
  action: string;                                 // TraceStep.action, or event kind + label
  now?: number;                                   // logical tick (spec) or ms (runtime)
  streams: Record<string, StreamState>;           // in, out, inner[k], per subscription
  subs?: Record<string, 'idle' | 'on' | 'off' | 'complete' | 'error'>;
  internals?: Record<string, unknown>;            // buffer, pending timer, refCount, active inners
}

type SvgElem = { name: string; attrs: Record<string, string>; children: SvgElem[] | string };
type View = (frame: FrameState) => SvgElem;       // pure, exactly like the TLA+ View

The element record is the module's own SVGElem, kept on purpose. It can be serialised to a string for a static page, exactly as SVGElemToString does, or built as real DOM through the framework-less JSX factory used in rxjs-ds, where <g> and <rect> produce SVG nodes directly. The animator is itself a small RxJS pipeline: key and button events folded by scan into a frame index, mapped to frames[i].

Decisions carried over, and the ones changed

Kept from the module

  • The View as a pure function of one state, composed from a handful of primitives and a grouping construct.
  • One frame per trace step, never interpolated. Frames are discrete because the semantics are.
  • An action label on every frame, now sourced from the checker or the event kind instead of hand annotations.
  • A stepper with keyboard control and a frame counter. It is the whole user interface and it is enough.

Changed for RxJS

  • Render in TypeScript, not in TLA+ string variables. tla-ts has no Java override for serialisation, and auxiliary state bloats the state space.
  • One generic layout, lanes on a shared time axis, instead of hand-placed coordinates per spec. Per-operator code is confined to the internals panel.
  • Render the current frame on demand rather than pre-rendering every frame as a hidden group. Runtime traces can run to thousands of events.
  • Two sources for the same frame type, so a model trace and a runtime trace of one scenario can be played side by side.

Frame anatomy

What a single frame should look like for the generic renderer, drawn for Take.tla at the step where the second value arrives. The lanes and marbles come from the stream variables; the subscription markers and counters come from the operator lane; the panel prints the spec's variables verbatim, which is what makes the picture checkable against the trace.

Gaps and cautions

  • No interactive exploration on the model track yet. tla-ts 0.0.3 exports a check function and a parser, with no public evaluate or single-step API, although an evaluator exists in its source. Choosing the next action at each state, the feature Schultz wished for and tla-web now has, would need that API first. The runtime track can be made interactive by driving the real operator under TestScheduler.
  • Logical versus real time. Specs step a now tick; the runtime records milliseconds. The RxOTN model already collapses recorded times into ordered columns, which is the right discretisation for both.
  • Higher-order operators need parent links. The event schema reserves parentSubscriptionId but does not yet populate it everywhere. Inner lanes under switchMap, mergeMap, concatMap and exhaustMap depend on it.
  • Values are opaque at runtime. The export boundary serialises values to JSON; the renderer should use the same serialiser so marbles label consistently across live and exported traces.
  • Frame count. Pre-rendering hidden groups is fine for a few hundred frames. Beyond that, keep the frame array and render one frame into a single SVG element.

Milestones

The six steps are the project's milestones, tracked on GitHub, ordered by dependency and by how much existing code each reuses.

  1. M1 · SVG frames over tla-ts tracesExtend trace-to-marble.mjs with a frame renderer and a ported stepper page. Animate the four bug demos in the specs manifest: mergeMap where switchMap was intended, the concatMap stall, the shareReplay leak and the combineLatest hang. A few hundred lines; the trace parsing already exists.
  2. M2 · Extract the frame type and the model adapterMove FrameState, SvgElem and fromTlaTrace into this repository as a package, with Vitest tests on the adapter against the fixture traces.
  3. M3 · Runtime adapterWrite fromExecutionTrace as a scan over ExecutionEvent[], reusing the lane classification from the rxotn package, and populate inner lanes from parent links.
  4. M4 · Animator componentsA framework-less JSX component for rxjs-ds and a matching Vue component for rxjs-vitepress-ds, so operator documentation pages can embed an animated counterexample.
  5. M5 · Model beside runtimePlay a spec counterexample and a TestScheduler recording of the same scenario in two synchronised steppers. The conformance tests in rxjs-operator-tla already pair the two.
  6. M6 · Interactive explorationBlocked on a step or evaluate API from tla-ts for the model track; available sooner on the runtime track through the scheduler.
